# Deferred Register

Living document per `CLAUDE.md` §0/§3.1: every unverified claim (`V-xx`) and deliberate
debt/postponement (`D-xx`) discovered during implementation lives here, ranked by
consequence within each list. Created in the same pass as
`docs/tasks/TASK-scaffold-monorepo.md`, the first task to postpone anything.

Update this file in the same pass that resolves an item — move it to "Resolved" with the
date and what was decided, don't just delete it.

| V-4 | `workers/Dockerfile`'s runtime stage actually contains a working `ffmpeg` binary and a correctly linked `libvips42`, and the built image runs as the non-root `worker` user (`TASK-ci-worker-image.md`). ## D-xx — Deliberate debt / postponements

| ID | Decision | Why deferred | Re-evaluation trigger |
|----|----------|---------------|-------------------------|
| D-1 | `proto/` (gRPC plugin contract) and `packages/` (shared TS types) are still **not** scaffolded, even though CLAUDE.md §4 proposes them as part of the eventual layout. The `apps/web` portion closed 2026-08-06 (`TASK-editor-scaffold.md`) — scaffolded via `pnpm create next-app@latest`. The Edit Recipe schema landed 2026-08-07 (`TASK-recipe-schema.md`) but **inside `apps/web`**, not `packages/` — see new `D-17`. | Phase 1 (spec's phasing) only needed the orchestrator and one Go worker type; Phase 2 (Editor MVP) needs `apps/web`, which is why that portion closed now. `proto/`/`packages/` still have no consumer — scaffolding them early risks drifting stale (framework/tooling versions moving on, per CLAUDE.md §2.0) before Phase 3/4 actually touch them. The recipe schema has only one consumer (`apps/web`) until Phase 3 wires it into the orchestrator for "Apply to Batch," so it didn't trigger `packages/` yet either — see `D-17`. | `proto/` at Phase 4 start (or earlier if Phase 3's "Apply to Batch" needs the recipe/pipeline contract formalized sooner). `packages/`: Phase 3, when `apps/orchestrator` needs to read/write recipes for Apply to Batch — at that point `RecipeStep`/`Recipe` moves from `apps/web/src/lib/recipe/` into `packages/` and both apps import the same definition instead of the two hand-kept-parallel shapes tracked in `D-17`. |
| D-2 | Root `package.json`'s `packageManager` field is pinned to `pnpm@11.5.2` (what was actually installed locally via nvm/corepack at scaffold time), not the `pnpm@11.14.x` line identified as current-stable during CLAUDE.md §2.0 research. | Both are the same major (pnpm 11) with no workspace-schema-breaking differences found during scaffolding; forcing a corepack download of a newer patch mid-scaffold added risk for no functional benefit. | Low urgency — revisit opportunistically, or immediately if a pnpm 11.14+-only feature (e.g. `pnpm doctor`, `pnpm lane`) becomes useful. |
| D-3 | Object storage choice (self-hosted MinIO vs. managed S3-compatible) — spec §"Open Questions," not resolved by this scaffold. | Not needed until Phase 3 (presigned upload flow) per spec's phasing; Phase 1's linear pipelines don't require object storage wiring yet. | Start of the Phase 3 task doc that implements presigned upload. |
| D-4 | Auth approach (reuse existing patterns vs. OAuth device flow) — spec §"Open Questions," not resolved by this scaffold. | Phase 1 (orchestrator + worker + Postgres + NATS, linear pipelines) has no user-facing auth surface yet per the spec's phasing. | Before any orchestrator endpoint needs to be gated — likely Phase 3 (realtime/SSE to specific users) or whenever multi-user access is first exercised. |
| D-5 | Plugin sandboxing tier (gRPC-only for v1 vs. pulling WASM/`wazero` into P0) — spec §"Open Questions," leaning P2 per the spec itself. | No plugin work happens before Phase 4. | Once the gRPC plugin contract (`proto/`) plumbing exists and a second/untrusted plugin author scenario is concretely being designed for (per the spec's own note: "worth revisiting once gRPC plumbing is done"). |

| D-8 | `StepDispatchMessage`/`StepResultMessage` are hand-duplicated as plain JSON shapes on both sides of the NATS boundary: `apps/orchestrator/src/jobs/dispatch-message.ts` (TS) and `workers/internal/dispatch/message.go` (Go), with no shared/generated contract (`TASK-nats-job-dispatch.md`). | `proto/` (the intended single source of truth for cross-language contracts, per CLAUDE.md §4) isn't scaffolded until Phase 4 per D-1. Re-evaluate sooner if the shapes actually drift out of sync and cause a bug — the hand-duplication is the risk this note exists to track. |
| D-9 | `plexus.jobs.dispatch` is one flat subject for every built-in processor type — no per-processor subject fan-out (e.g. `plexus.jobs.dispatch.image.resize`), even though the spec's Core Concepts allows arbitrary processor ids (`TASK-nats-job-dispatch.md` §1). | Phase 1 is explicitly "single Go worker type" per the spec's phasing — one worker pool already consumes everything, so per-processor routing has no consumer to route to yet. | Once external plugins (Phase 4, alongside D-1's `proto/` and D-5's plugin sandboxing) need different processor types routed to different consumers/languages. |

| D-11 | `image.resize`/`image.convert`/`image.compress` read `inputRef` and write `outputRef` as literal local filesystem paths under `WORKER_STORAGE_DIR` (`workers/internal/processors/output.go`), not object storage (`TASK-builtin-processors.md`). | D-3 (object storage self-hosted vs. managed) isn't resolved until Phase 3's presigned-upload work; this task only needs processors to actually run, not a real upload/download flow. | D-13 | `image.resize` requires both `width` and `height`; single-dimension resize (scale by one dimension, preserve aspect) is not supported (`TASK-builtin-processors.md`). | govips's `Thumbnail`/`ThumbnailWithSize` API takes both dimensions; the idiomatic way to get single-dimension resize (an artificially large value for the unconstrained dimension) is a real pattern for other libvips bindings but wasn't verified against this specific govips version, and CLAUDE.md §0 forbids inventing library behavior. | Before any editor/pipeline UI needs "resize by width only" — `[VERIFY]` the oversized-dimension idiom against govips's own tests/docs first, or find an official single-dimension API, before implementing. |
| D-15 | `video.transcode`/`video.compress` support exactly `mp4` (h264/aac) and `webm` (vp9/opus); `audio.extract`/`audio.convert` support exactly `mp3`/`aac`/`opus` (+`wav` for convert). No h265, av1, flac, or alac (`TASK-video-audio-processors.md`). | Same reasoning as the four fixed image formats in slice 3 — these are the pairs the spec's P0 line and examples actually need, not ffmpeg's full encoder surface (CLAUDE.md's "no code for hypothetical requirements"). | Whenever a concrete use case needs another codec — additive change to `videoCodecsForContainer`/`audioCodecForFormat` in `workers/internal/processors/ffmpeg.go`, not a redesign. |
| D-16 | `workers/Dockerfile` builds a worker image (`TASK-ci-worker-image.md`), but nothing pushes it to a registry or wires it into any deploy pipeline — no `docker build`/`push` step in `ci.yml`, no registry chosen. | Choosing a registry/deploy target is its own decision (comparable in shape to the spec's still-open object-storage question, D-3) and wasn't needed to prove CI itself. | Whenever Phase 1 moves from "runs locally / in CI" to "deployed somewhere" — needs a registry decision first. |
| D-17 | The Edit Recipe type (`apps/web/src/lib/recipe/schema.ts`, Zod) is hand-kept parallel to the orchestrator's pipeline step shape (`StepDto`/`PipelineStepDefinition` in `apps/orchestrator/src/pipelines/dto/create-pipeline.dto.ts` and `apps/orchestrator/src/db/schema.ts`, `class-validator`) rather than sharing one definition — two different files, two different validation libraries, in two different languages (`TASK-recipe-schema.md`). Same category of debt as `D-8`'s NATS message duplication. | `packages/` isn't scaffolded yet (`D-1`) and the recipe schema has only one real consumer today (`apps/web`) — Phase 2 has no orchestrator/batch integration. Recipe params are also typed per-processor (a discriminated union) rather than `StepDto`'s untyped `Record<string, unknown>`, a deliberate divergence for the live-preview and composite-slider work, not something a naive shared type could paper over without also changing the orchestrator's validation. | Phase 3, when `apps/orchestrator` needs to consume editor recipes for "Apply to Batch" (same trigger as `D-1`'s `packages/` update) — promote `apps/web/src/lib/recipe/schema.ts` into `packages/` and have both apps import it. Re-evaluate sooner if the two shapes actually drift and cause a bug. |
| D-18 | The live preview renderer (`apps/web/src/lib/preview/`) treats `image.convert`/`image.compress` recipe steps as a **visual passthrough** — no shader attempts to simulate JPEG/WebP/AVIF quantization artifacts or format-conversion appearance per-frame (`TASK-preview-renderer.md`). Only `image.resize` gets real geometric preview treatment. | Format is a container choice and `quality` only affects lossy-encoding artifacts that exist after a real encode pass — simulating that live would mean inventing codec/browser behavior CLAUDE.md §0 already warns against, for a feature (visible "JPEG quality" live preview, à la Photoshop's "Save for Web") nobody has asked for; Apple Photos itself doesn't expose it either. | If a future editor-UX task (distinct from `D-6`'s composite sliders) wants users to see compression artifacts live — e.g. a "file size vs. quality" control — needing either a debounced real-time re-encode preview or an approximated-artifact shader, neither attempted here. |
